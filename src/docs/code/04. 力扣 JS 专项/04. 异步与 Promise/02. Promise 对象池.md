# Promise 对象池

> 难度：中等 | 标签：Promise、并发控制 | LeetCode 2636（VIP 专属题） · [原题链接](https://leetcode.cn/problems/promise-pool/)

## 题目描述

> 本题为 LeetCode VIP 专属题，官方题面需登录后查看，以下为按原题题意整理的版本。

请你编写一个异步函数 `promisePool`，它接收一个异步函数数组 `functions` 和一个 **池限制** `n`。它应该返回一个 promise 对象，当所有输入函数都执行完毕后，该 promise 对象才解析。

**池限制** 定义为一次可以挂起的最多 promise 对象的数量。`promisePool` 应该先执行尽可能多的函数，并在旧的 promise 执行完毕后继续执行新函数。它应该先执行 `functions[i]`，再执行 `functions[i + 1]`，然后执行 `functions[i + 2]`，以此类推。当最后一个 promise 执行完毕时，`promisePool` 也应该执行完毕。

例如，如果 `n = 1`，`promisePool` 会按顺序每次执行一个函数；而如果 `n = 2`，它先执行两个函数，当两个函数中的任何一个执行完毕后，再执行第三个函数（如果它是可用的），依此类推，直到没有函数要执行为止。

你可以假设所有的 `functions` 都不会被拒绝。对于 `promisePool` 来说，返回一个可以解析任何值的 promise 都是可以接受的。

**示例 1：**

```
输入：
functions = [
  () => new Promise(res => setTimeout(res, 300)),
  () => new Promise(res => setTimeout(res, 400)),
  () => new Promise(res => setTimeout(res, 200))
]
n = 2
输出：[[300,400,500],500]
解释：
传递了三个函数。它们的睡眠时间分别为 300ms、400ms 和 200ms。
它们分别在 300ms、400ms 和 500ms 时执行完毕，返回的 promise 在 500ms 时解析。
在 t=0 时，执行前两个函数，池大小达到限制 2。
在 t=300 时，第一个函数执行完毕，执行第三个函数，池大小为 2。
在 t=400 时，第二个函数执行完毕，没有可执行的函数了，池大小为 1。
在 t=500 时，第三个函数执行完毕，池大小为 0，因此返回的 promise 也执行完毕。
```

**示例 2：**

```
输入：
functions = [
  () => new Promise(res => setTimeout(res, 300)),
  () => new Promise(res => setTimeout(res, 400)),
  () => new Promise(res => setTimeout(res, 200))
]
n = 5
输出：[[300,400,200],400]
解释：
三个输入的 promise 分别在 300ms、400ms、200ms 时执行完毕，返回的 promise 在 400ms 时解析。
在 t=0 时，执行所有 3 个函数，池限制 5 永远不会被触及。
在 t=200 时，第三个函数执行完毕，池大小为 2。
在 t=300 时，第一个函数执行完毕，池大小为 1。
在 t=400 时，第二个函数执行完毕，池大小为 0，因此返回的 promise 也执行完毕。
```

**示例 3：**

```
输入：
functions = [
  () => new Promise(res => setTimeout(res, 300)),
  () => new Promise(res => setTimeout(res, 400)),
  () => new Promise(res => setTimeout(res, 200))
]
n = 1
输出：[[300,700,900],900]
解释：
在 t=0 时，执行第一个函数，池大小为 1。
在 t=300 时，第一个函数执行完毕，执行第二个函数，池大小为 1。
在 t=700 时，第二个函数执行完毕，执行第三个函数，池大小为 1。
在 t=900 时，第三个函数执行完毕，池大小为 0，因此返回的 promise 也执行完毕。
```

**提示：**

- `0 <= functions.length <= 10`
- `1 <= n <= 10`

## 题解

::: details 点击查看题解

### 思路

整体策略是「工作池」：启动 `n` 个 worker，每个 worker 用一个 `while` 循环不断领取下一个任务（游标 `index++`），直到领完为止；外层 `await Promise.all(workers)`，保证所有任务结束后 `promisePool` 才解析。

「完成即补位」是池语义的核心：worker `await` 当前任务一结束就立刻进入下一轮领取，任意时刻在跑的任务数不超过 `n`，且只要有任务结束、还有剩余任务就会补满。`n = 1` 时只有一个 worker，退化为完全串行（示例 3）；`n` 不小于任务数时所有任务同时启动（示例 2）。

执行顺序天然是 `functions[i]` → `functions[i + 1]`：游标单调递增，先领取的先启动，与完成顺序无关，正好满足题面的顺序要求。

为什么不写成「按批 `Promise.all`」（旧页「并发控制 limitConcurrency」讨论过这个取舍）：那样要等一批里最慢的任务结束才启动下一批，慢任务会拖累整体吞吐；worker 池是「谁先结束谁先补位」，示例 1 中 300ms 一到第三个函数立即顶上，正是这个效果。

任务工厂必须「由 `promisePool` 决定何时调用」（旧页 Scheduler 的要点）：如果 `functions` 里放的是 Promise 实例，数组构造那一刻全部任务已经启动，池限制就完全失去意义——这也是所有并发控制类题目的通用前提。

边界：`functions` 为空时所有 worker 立即退出，`Promise.all([])` 立即解析；本题保证 `functions` 不会 reject，若要健壮可在 `await` 外包 try/catch，或按旧页「失败不中断、收集每个状态」的思路改造，但本题签名只需「全部执行完毕即解析」。

### 代码实现

```javascript
/**
 * @param {Array<() => Promise<any>>} functions
 * @param {number} n
 * @return {Promise<any>}
 */
var promisePool = async function(functions, n) {
  let index = 0; // 游标：下一个待领取的任务下标

  // 每个 worker 循环领任务：完成即补位，直到没有任务可领
  async function worker() {
    while (index < functions.length) {
      const current = index++;
      await functions[current]();
    }
  }

  // 最多启动 n 个 worker；任务数不足 n 时多出的 worker 会立即退出
  const workers = [];
  for (let i = 0; i < n; i++) {
    workers.push(worker());
  }
  await Promise.all(workers); // 最后一个任务完成后 promisePool 才解析
};
```

### 复杂度分析

- 时间复杂度：O(m)，m 为 `functions.length`，每个任务恰好被调用并等待一次。
- 空间复杂度：O(n)，同时存活的 worker 协程数（外加 `Promise.all` 持有的 n 个 promise）。
