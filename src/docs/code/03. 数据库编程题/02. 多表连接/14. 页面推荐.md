# 页面推荐

> 难度：中等 | 标签：多表连接、子查询 | [LeetCode 原题](https://leetcode.cn/problems/page-recommendations/)

## 题目描述

> 本题为 LeetCode VIP 专属题，题面根据表结构与测试数据整理。

表 `Friendship`：

```
+---------------+---------+
| Column Name   | Type    |
+---------------+---------+
| user1_id      | int     |
| user2_id      | int     |
+---------------+---------+
(user1_id, user2_id) 是该表的主键（具有唯一值的列的组合）。
该表的每一行表示 user1_id 和 user2_id 之间存在好友关系。
```

表 `Likes`：

```
+-------------+---------+
| Column Name | Type    |
+-------------+---------+
| user_id     | int     |
| page_id     | int     |
+-------------+---------+
(user_id, page_id) 是该表的主键（具有唯一值的列的组合）。
该表的每一行表示 user_id喜欢了 page_id。
```

编写解决方案，**为 `user_id = 1` 的用户推荐页面**：候选是他好友喜欢的页面，但 **不能推荐他已经喜欢过的页面**。

返回结果表 **无顺序要求，且不能有重复**。

结果格式如下所示。

**示例 1：**

```
输入：
Friendship 表：
+----------+----------+
| user1_id | user2_id |
+----------+----------+
| 1        | 2        |
| 1        | 3        |
| 1        | 4        |
| 2        | 3        |
| 2        | 4        |
| 2        | 5        |
| 6        | 1        |
+----------+----------+
Likes 表：
+---------+---------+
| user_id | page_id |
+---------+---------+
| 1       | 88      |
| 2       | 23      |
| 3       | 24      |
| 4       | 56      |
| 5       | 11      |
| 6       | 33      |
| 2       | 77      |
| 3       | 77      |
| 6       | 88      |
+---------+---------+
输出：
+------------------+
| recommended_page |
+------------------+
| 23               |
| 24               |
| 56               |
| 33               |
| 77               |
+------------------+
解释：
用户 1 的好友是 2、3、4、6。
候选页面：来自用户 2 的 23、来自用户 3 的 24、来自用户 4 的 56、来自用户 6 的 33。
页面 77 同时被好友 2 和 3 喜欢，只推荐一次。
页面 88 虽然被好友 6 喜欢，但用户 1 已经喜欢了，因此不推荐。
```

## 题解

::: details 点击查看题解

### 思路

拆成三个条件的交集：**是用户 1 的好友喜欢的** ∩ **不是用户 1 自己喜欢的** ∩ **去重**。

第一步「找好友」最容易出错：`Friendship` 是 **无向** 的，好友关系既可能记成 `(1, 2)` 也可能记成 `(6, 1)`，只查 `user1_id = 1` 会漏掉 6 号。要么 `WHERE user1_id = 1 OR user2_id = 1` 然后用 `CASE WHEN` 归一出对端，要么按官方写法把两个方向 `UNION` 起来：`SELECT user1_id FROM Friendship WHERE user2_id = 1 UNION SELECT user2_id FROM Friendship WHERE user1_id = 1`。漏掉一个方向，示例里的 33 就不会出现。

第二步拿好友 id 去 `Likes` 里取页面；第三步用 `NOT IN (SELECT page_id FROM Likes WHERE user_id = 1)` 排除自己已喜欢的 88。这里 `NOT IN` 的 NULL 陷阱同样存在（子查询含 `NULL` 则整体失效），本题 `page_id` 非空所以安全，换成 `NOT EXISTS` 更稳。最后 **`DISTINCT` 不能忘**：页面 77 被两个好友同时喜欢，不去重会输出两行，题目明确要求无重复。

整体顺序上，先用 CTE 或子查询把「好友集合」物化出来，再连接 `Likes`、再排除，层次最清楚；写成一个巨大的嵌套 `IN` 也能通过，但可读性差。替代写法：`LEFT JOIN (用户 1 喜欢的页面) own ON l.page_id = own.page_id WHERE own.page_id IS NULL`，与 183 题的判空套路同源。

### SQL 实现

```sql
WITH friends AS (
    SELECT user1_id AS user_id FROM Friendship WHERE user2_id = 1
    UNION
    SELECT user2_id FROM Friendship WHERE user1_id = 1
)
SELECT DISTINCT l.page_id AS recommended_page
FROM friends f
JOIN Likes l ON f.user_id = l.user_id
WHERE l.page_id NOT IN (
    SELECT page_id FROM Likes WHERE user_id = 1
);
```

### 复杂度分析

- 时间复杂度：O(f + k)，f 为好友关系行数、k 为好友的点赞记录数，去重依赖哈希或排序。
- 空间复杂度：O(p)，p 为推荐页面数量，`DISTINCT` 的去重开销。
