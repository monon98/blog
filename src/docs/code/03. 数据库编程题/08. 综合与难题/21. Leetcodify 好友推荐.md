# Leetcodify 好友推荐

> 难度：困难 | 标签：多表连接、分组聚合、子查询 | [LeetCode 原题](https://leetcode.cn/problems/leetcodify-friends-recommendations/)

## 题目描述

> 本题为 LeetCode VIP 专属题，题面根据表结构与测试数据整理。

表：`Listens`

```
+-------------+---------+
| Column Name | Type    |
+-------------+---------+
| user_id     | int     |
| song_id     | int     |
| day         | date    |
+-------------+---------+
该表没有主键，因此会存在重复的行。
该表的每一行表示用户 user_id 在 day 这一天收听了歌曲 song_id。
```

表：`Friendship`

```
+---------------+---------+
| Column Name   | Type    |
+---------------+---------+
| user1_id      | int     |
| user2_id      | int     |
+---------------+---------+
(user1_id, user2_id) 是该表的主键。
该表的每一行表示 user1_id 和 user2_id 是好友。
注意：user1_id < user2_id。
```

写出 SQL 语句，为 Leetcodify 用户推荐好友。将符合下列条件的用户 x 推荐给用户 y：

- 用户 x 和 y 不是好友，且
- 用户 x 和 y 在同一天收听了相同的三首或更多不同歌曲。

注意，好友推荐是单向的：如果用户 x 和用户 y 应当互相推荐，结果表需要同时包含「x 推荐给 y」和「y 推荐给 x」两行；另外结果表不得出现重复项。按任意顺序返回结果表。

**示例 1：**

输入：

```
Listens 表：
+---------+---------+------------+
| user_id | song_id | day        |
+---------+---------+------------+
| 1       | 10      | 2021-03-15 |
| 1       | 11      | 2021-03-15 |
| 1       | 12      | 2021-03-15 |
| 2       | 10      | 2021-03-15 |
| 2       | 11      | 2021-03-15 |
| 2       | 12      | 2021-03-15 |
| 3       | 10      | 2021-03-15 |
| 3       | 11      | 2021-03-15 |
| 3       | 12      | 2021-03-15 |
| 4       | 10      | 2021-03-15 |
| 4       | 11      | 2021-03-15 |
| 4       | 13      | 2021-03-15 |
| 5       | 10      | 2021-03-16 |
| 5       | 11      | 2021-03-16 |
| 5       | 12      | 2021-03-16 |
+---------+---------+------------+

Friendship 表：
+----------+----------+
| user1_id | user2_id |
+----------+----------+
| 1        | 2        |
+----------+----------+
```

输出：

```
+---------+----------------+
| user_id | recommended_id |
+---------+----------------+
| 1       | 3              |
| 2       | 3              |
| 3       | 1              |
| 3       | 2              |
+---------+----------------+
```

解释：

- 用户 1 和 2 在同一天收听了歌曲 10、11、12，但他们已经是好友，因此不推荐。
- 用户 1 和 3 在同一天收听了歌曲 10、11、12，且不是好友，因此互相推荐。
- 用户 1 和 4 没有收听三首相同的歌曲。
- 用户 1 和 5 收听了歌曲 10、11、12，但不是在同一天收听的。
- 类似地，用户 2 和 3 在同一天收听了三首相同歌曲且不是好友，也互相推荐。

## 题解

::: details 点击查看题解

### 思路

推荐条件有两条：「同一天至少 3 首相同歌曲」与「两人尚非好友」。先解决第一条——把 `Listens` 自连接，连接条件是同一天、同一首歌、且是两个不同的用户，再按（天、用户 A、用户 B）分组统计去重歌曲数，`HAVING COUNT(DISTINCT song_id) >= 3` 就得到了所有候选的有向用户对。这里 `l1.user_id <> l2.user_id` 绝不能少：`Listens` 没有主键，同一用户同天听同一首歌的记录自己配自己也会凑够 3 首，凭空产生 `(x, x)` 这样的「自我推荐」。

第二条好友排除有个坑：`Friendship` 是无向关系，但只存 `user1_id < user2_id` 的单向行，直接按 `(l1.user_id, l2.user_id) = (user1_id, user2_id)` 匹配会漏掉反向边——比如候选对 (3, 1) 就匹配不到好友行 (1, 2) 之外的任何一对。标准做法是先用 `UNION` 把好友表展开成双向有序对，再用 `NOT EXISTS` 排除；写成 `LEFT JOIN ... IS NULL` 效果等价。

最后两个去重点：分组是带 `day` 的（「同一天」这个条件是按天判定的），同一对用户可能在多天都满足条件、输出多行，所以最外层要 `DISTINCT`；题目也明确要求结果表不能有重复项。替代写法：先聚合出候选对再 `LEFT JOIN` 好友表筛 `IS NULL`，或先用 `l1.user_id < l2.user_id` 配对聚合后 `UNION` 出反向——主解法的写法最直观。

### SQL 实现

```sql
WITH T AS (
    SELECT user1_id, user2_id FROM Friendship
    UNION
    SELECT user2_id AS user1_id, user1_id AS user2_id FROM Friendship
)
SELECT DISTINCT l1.user_id, l2.user_id AS recommended_id
FROM Listens AS l1
JOIN Listens AS l2
    ON l1.day = l2.day AND l1.song_id = l2.song_id AND l1.user_id <> l2.user_id
WHERE NOT EXISTS (
    SELECT 1 FROM T AS t
    WHERE t.user1_id = l1.user_id AND t.user2_id = l2.user_id
)
GROUP BY l1.day, l1.user_id, l2.user_id
HAVING COUNT(DISTINCT l1.song_id) >= 3;
```

### 复杂度分析

- 时间复杂度：O(m²)，m 为 `Listens` 行数，自连接在同一天同一首歌的记录之间配对；好友排除配合索引近似 O(f)。
- 空间复杂度：O(f + u²)，f 为好友关系数（双向展开后翻倍），u 为参与推荐的用户对数。
