# 面试难题汇总

## 1. 前端如何分析内存泄漏？

::: details

内存泄漏是指程序在运行过程中，不再使用的内存没有被释放，导致可用内存逐渐减少，最终可能导致应用程序崩溃或性能下降。在前端开发中，分析和修复内存泄漏是一个重要的任务。以下是一些常用的方法和工具，用于检测和分析前端的内存泄漏。

### 1. 使用浏览器的开发者工具

大多数现代浏览器都提供了强大的开发者工具，可以帮助你检测内存泄漏。

#### Chrome 浏览器

1. **打开开发者工具**：
   - 右键点击页面，选择"检查"或按 `F12`。

2. **切换到"Memory"面板**：
   - 在开发者工具中，找到并点击"Memory"标签。

3. **创建快照**：
   - 点击"Take snapshot"按钮，生成当前内存使用情况的快照。
   - 进行一些操作后，再次创建快照。

4. **比较快照**：
   - 通过比较两个快照，查看哪些对象的数量增加了，可能是内存泄漏的迹象。
   - 你可以查看对象的引用关系，找出未被释放的对象。

5. **使用"记录分配"**：
   - 在"Memory"面板中，选择"Record Allocation Timeline"选项，记录一段时间内的内存分配情况。
   - 进行一些操作后停止记录，查看内存使用情况的变化。

#### Firefox 浏览器

Firefox 的操作与 Chrome 类似，使用"内存"面板进行快照和比较。

### 2. 监控性能

通过监控应用程序的性能，可以间接发现内存泄漏。你可以使用 `performance.memory` API（仅在 Chrome 中可用）来查看 JavaScript 堆的使用情况。

```javascript
if (performance.memory) {
    console.log(`JS Heap Size Limit: ${performance.memory.jsHeapSizeLimit}`);
    console.log(`Total JS Heap Size: ${performance.memory.totalJSHeapSize}`);
    console.log(`Used JS Heap Size: ${performance.memory.usedJSHeapSize}`);
}
```

### 3. 代码审查

- **事件监听器**：确保在不再需要时移除事件监听器，尤其是在组件销毁时。
- **定时器和异步操作**：确保在组件卸载时清除定时器和取消未完成的异步操作。
- **全局变量**：避免使用全局变量，确保变量的作用域正确。
- **闭包**：注意闭包可能导致的内存泄漏，确保不再使用的变量被释放。

### 4. 总结

内存泄漏是前端开发中的常见问题，通过使用浏览器的开发者工具、监控性能和代码审查，可以有效地检测和分析内存泄漏。及时发现并修复内存泄漏，可以提高应用程序的性能和稳定性。
:::

## 2. 什么是闭包？闭包的优缺点是什么？

::: details
闭包（Closure）是 JavaScript 中一个重要的概念，它指的是一个函数与其外部作用域（lexical scope）中的变量的绑定关系。简单来说，闭包允许一个函数访问并操作其外部函数的变量，即使外部函数已经执行完毕。

### 闭包的工作原理

当一个函数被定义在另一个函数内部时，内部函数就形成了一个闭包。这个闭包可以访问外部函数的变量，即使外部函数已经返回。闭包的形成使得内部函数可以"记住"外部函数的状态。

### 闭包的示例

```javascript
function outerFunction() {
    let outerVariable = 'I am from outer function';

    function innerFunction() {
        console.log(outerVariable); // 访问外部函数的变量
    }

    return innerFunction; // 返回内部函数
}

const closureFunction = outerFunction(); // 执行外部函数，返回内部函数
closureFunction(); // 输出: I am from outer function
```

### 闭包的优点

1. **数据封装**：闭包可以创建私有变量，外部无法直接访问这些变量，只能通过特定的函数进行操作。这有助于实现数据的封装和保护。

   ```javascript
   function createCounter() {
       let count = 0; // 私有变量

       return {
           increment: function() {
               count++;
               return count;
           },
           decrement: function() {
               count--;
               return count;
           },
           getCount: function() {
               return count;
           }
       };
   }

   const counter = createCounter();
   console.log(counter.increment()); // 输出: 1
   ```

2. **保持状态**：闭包可以保持外部函数的状态，允许你在后续的调用中继续使用这些状态。

3. **函数工厂**：通过闭包，可以创建具有特定行为的函数，例如函数工厂，根据不同的参数生成不同的函数。

### 闭包的缺点

1. **内存消耗**：闭包会保持对外部变量的引用，这可能导致内存泄漏，特别是在不再需要闭包时。如果闭包引用了大量数据，可能会导致内存占用增加。

2. **性能问题**：过多的闭包可能会影响性能，尤其是在频繁创建和销毁的情况下。每个闭包都需要维护其外部作用域的状态，这可能会增加内存和处理开销。

3. **调试复杂性**：由于闭包的作用域链，调试时可能会变得复杂，尤其是在嵌套函数较多的情况下，追踪变量的来源和状态可能会比较困难。

### 总结

闭包是 JavaScript 中一个强大且灵活的特性，它允许函数访问其外部作用域的变量，并能保持这些变量的状态。通过合理使用闭包，可以实现数据封装、函数工厂等多种编程模式。然而，开发者在使用闭包时也需要注意内存管理和性能问题，以避免潜在的缺陷。理解闭包的工作原理对于深入掌握 JavaScript 至关重要。
:::

## 3. route 中的 history 和 hash 的区别是什么？各自的优点和缺点是什么？

::: details
在 Vue.js 中，路由中的 `history` 模式和 `hash` 模式是两种常见的路由模式，它们有一些区别和各自的优缺点。

1. **区别**：
   - `hash` 模式：在 URL 中会出现 `#` 符号，路由信息会保存在 URL 的哈希部分，例如 `http://www.example.com/#/about`。
   - `history` 模式：利用 HTML5 的 History API，在 URL 中不会有 `#` 符号，路由信息会直接显示在路径中，例如 `http://www.example.com/about`。

2. **优点和缺点**：
   - `hash` 模式：
     - 优点：
       - 兼容性好，支持所有浏览器。
       - 部署简单，不需要服务器端额外配置。
     - 缺点：
       - URL 中会有 `#` 符号，影响美观性。
       - 不利于 SEO（搜索引擎优化），搜索引擎对于 `#` 后面的内容不会进行解析。
   - `history` 模式：
     - 优点：
       - URL 更美观，不会有 `#` 符号。
       - 更符合 RESTful 风格，路径更加直观。
     - 缺点：
       - 兼容性较差，需要服务器端的额外配置支持。
       - 刷新页面时会出现 404 错误，需要配置后端服务器以支持单页应用的路由。

综上所述，如果你的应用需要在老旧浏览器中运行或者不需要考虑 SEO 问题，可以选择 `hash` 模式；如果你追求更好的用户体验和更好的 URL 显示，可以选择 `history` 模式，但需要注意处理刷新页面时出现的问题。
:::

## 4. JS 超过 Number 最大值的数怎么处理？

::: details
**问题**：JavaScript 中遇到超过 Number.MAX_SAFE_INTEGER（2^53 - 1）的大数怎么办？

### 解决方案

1. **BigInt**：ES2020 引入的原生大整数类型
   - 字面量写法：9007199254740993n
   - 或 BigInt('9007199254740993')
   - 注意：BigInt 不能与 Number 直接混合运算

2. **第三方库**：decimal.js、big.js、bignumber.js
   - 适合需要小数精度计算的场景（如金额）
   - 提供丰富的运算方法

3. **转字符串传输**
   - 后端返回 ID 时序列化为字符串
   - 避免 JSON.parse 时精度丢失

### 实际场景

- 后端雪花算法生成的长整型 ID 必须以字符串形式下发
- JSON.parse 可用 json-bigint 库处理已存在的精度丢失数据

:::

## 5. 如何解决页面请求接口大规模并发问题？

::: details
**问题**：页面初始化时触发大量接口请求，如何优化？

### 前端手段

1. **请求队列**：控制最大并发数，排队执行多余请求
2. **防抖/节流**：减少高频触发的重复请求
3. **分页/滚动加载**：只请求可视区域需要的数据
4. **合并请求**：BFF 层聚合多个小接口为一次请求
5. **缓存复用**：相同参数的请求共享同一个 Promise（去重）

### 服务端配合

- 接口限流保护后端
- CDN 分担静态资源压力
- 缓存热点数据

:::

## 6. 请说说大文件上传

::: details
**问题**：如何设计一个大文件上传方案？（如 1GB 视频）

### 核心思路：切片上传

1. 使用 File.slice() 将文件切成固定大小的块（如 5MB）
2. 逐块或并发上传，每块携带索引信息
3. 服务端接收分片并保存，全部完成后合并

### 断点续传

- 上传前先请求服务端已接收的分片列表（基于文件 hash 标识唯一性）
- 只上传缺失的分片
- 文件 hash 计算：Web Worker 中用 spark-md5 增量计算，避免阻塞主线程

### 其他要点

- 断开重连重传：失败分片自动重试（限制次数）
- 进度展示：已上传分片数 / 总分片数
- 暂存技术栈：Web Worker 计算 hash → Blob 切片 → IndexedDB 记录进度

:::

## 9. 如何修改第三方 npm 包？

::: details
**问题**：第三方包有 bug 或不满足需求，又不能等官方修复，怎么办？

### 方案对比

1. **直接改 node_modules**：不可取，重新安装即失效
2. **patch 方案**（推荐）：patch-package
   - 修改 node_modules 中的代码
   - npx patch-package 包名 生成补丁文件
   - package.json 配置 postinstall 钩子自动应用补丁
   - pnpm 有原生 patch 支持：pnpm patch
3. **Fork 维护**：fork 后自行维护，npm 安装自己的仓库地址
   - 适合长期大量定制

### 选择原则

- 小改动临时方案 → patch-package
- 长期深度定制 → fork 自维护
- 通用能力 → 给上游提 PR

:::

## 10. 使用同一个链接，PC 打开是 Web 应用、手机打开是 H5 应用，如何实现？

::: details
**问题**：同一 URL 如何按设备类型呈现不同应用？

### 方案一：UserAgent 检测（常用）

- 服务端或客户端通过 navigator.userAgent 判断设备类型
- 服务端判断后重定向到对应版本（302 → m.example.com）
- 客户端判断后在入口处加载不同的应用 bundle

### 方案二：响应式一套代码

- 媒体查询 + 弹性布局自适应两端
- 优点：一个应用好维护；缺点：复杂交互难以兼顾

### 注意事项

- userAgent 可伪造，关键业务不要依赖它做权限判断
- 重定向要保留原始路径和查询参数

:::

## 11. 当 QPS 达到峰值时，该如何处理？

::: details
**问题**：系统 QPS 达到峰值，从前端和服务端角度分别怎么应对？

### 前端侧

1. **请求限流**：客户端主动控制请求频率
2. **请求合并**：防抖节流减少无效请求
3. **请求缓存**：SWR 策略，先返回缓存再后台更新
4. **降级非核心功能**：关闭轮询、延迟加载非关键模块

### 服务端侧

1. **限流**：网关层令牌桶/漏桶算法
2. **任务队列**：削峰填谷（如视频转码用 Bull 队列异步处理）
3. **扩容**：水平扩容 + 负载均衡
4. **多级缓存**：本地缓存 → Redis → 数据库
5. **熔断降级**：核心链路保护，非核心服务降级

:::

## 14. Web 应用中如何对静态资源加载失败的场景做降级处理？

::: details
**问题**：CDN 挂了或网络异常导致静态资源加载失败，如何降级？

### 分类处理

1. **图片**：占位符、alt 提示、onerror 重试或换源
2. **CSS 文件**：关键样式内联到 HTML（Critical CSS），加载失败不影响基本布局
3. **JavaScript 文件**：核心脚本内联；CDN 资源监听 error 后动态切换备用域名重新注入
4. **CDN**：多 CDN 厂商容灾，运行时探测自动切换
5. **字体文件**：font-display: swap 先用降级字体渲染
6. **服务端渲染失败**：降级输出客户端渲染壳子或静态兜底页

### 监控上报

- window.addEventListener('error') 捕获资源加载错误
- 上报错误日志，触发告警

:::

## 16. 请说说你对函数式编程思想的理解？

::: details
**问题**：什么是函数式编程？它的优势和劣势是什么？

### 核心概念

1. **纯函数**：相同输入永远得到相同输出，无副作用
2. **不可变性**：数据一旦创建不再修改，变更返回新数据
3. **高阶函数**：接收函数作为参数或返回函数
4. **柯里化与函数组合**：拆分与组合小函数构建复杂逻辑

### 优势

1. 可测试性强：纯函数易于单元测试
2. 可维护性好：无隐藏状态依赖，行为可预测
3. 天然适合并发：无共享可变状态，无锁竞争
4. 代码简洁：声明式表达意图

### 在 JS 中的应用

- Array 的 map/filter/reduce 即函数式风格
- Redux 强制 reducer 为纯函数
- Ramda 等工具库提供 curry/compose
- 详细展开见 [函数式编程专题](./01.%20javascript/13.%20函数式编程)

:::

## 17. 请说说你对 DNS 协议的理解？域名解析整个过程

::: details
**问题**：描述 DNS 域名解析的完整流程。

### 什么是 DNS

- Domain Name System：将域名映射到 IP 地址的应用层协议
- 默认端口 53，UDP 为主（区域传送用 TCP）

### 解析流程

1. 用户输入域名
2. 检查浏览器自身 DNS 缓存
3. 检查操作系统 DNS 缓存（hosts 文件）
4. 询问本地 DNS 服务器（运营商提供，有缓存则直接返回）
5. 本地 DNS 未命中时发起迭代查询：根 DNS 服务器 → 顶级域（TLD）服务器 → 权威 DNS 服务器
6. 返回 IP 结果，各级缓存，浏览器向该 IP 发起请求

### 递归查询与迭代查询

- 客户端 → 本地 DNS：递归查询（必须给出最终结果）
- 本地 DNS → 各级服务器：迭代查询（逐级引导）

### 相关优化

- dns-prefetch 预解析
- HTTPDNS 绕过运营商 LocalDNS 的劫持与调度不准问题

:::

## 18. 请说说图片性能优化的方案

::: details
**问题**：图片往往是页面最大的资源瓶颈，如何优化？

### 加载时机

1. loading="lazy"：原生懒加载
2. Intersection Observer：自定义懒加载（兼容旧浏览器可退化为 scroll 监听）
3. 首屏关键图 preload 提前加载

### 格式与体积

- 现代格式：WebP / AVIF（同等质量体积更小）
- 响应式图片：srcset + sizes 按屏幕加载合适尺寸
- 构建期压缩 + CDN 内容压缩

### 渲染稳定

- 显式设置 width/height 避免 CLS
- 占位色块或模糊缩略图（LQIP）提升感知性能

:::

## 19. 移动端上拉加载、下拉刷新的实现方案

::: details
**问题**：移动端长列表的上拉加载更多、下拉刷新如何实现？

### 核心原理

1. **滚动事件监听**：监听 scroll（或 Intersection Observer 替代）
2. **触底判断**：scrollTop + clientHeight >= scrollHeight - 阈值
3. **下拉刷新**：touchstart/touchmove 记录位移，超过阈值松手触发刷新回调
4. **回调触发加载**：请求完成后追加数据

### 性能考虑

- 节流滚动事件处理
- 配合虚拟列表只渲染可视区
- 加载中锁定标志防止重复触发

### 用户体验

- 下拉指示器视觉反馈 + 回弹动画
- 底部 loading / 没有更多了提示
- 错误时提供点击重试

### 现成方案

- better-scroll、vant 的 List/PullRefresh 组件

:::

## 21. window 对象上频繁绑定内容，有什么风险？

::: details
**问题**：为什么不应该往 window 上挂大量全局变量？

### 风险

1. **命名冲突**：window.hello 这类命名可能覆盖第三方库或未来原生 API
2. **全局污染**：任何脚本都能读写，状态不可控
3. **安全风险**：暴露内部方法给控制台，可被任意调用
4. **性能问题**：全局对象属性增加内存开销且永不回收（除非手动置 null）

### 解决方案

1. **模块化**：ES Module 天然隔离作用域（首选）
2. **命名空间**：单一全局对象挂载子属性
3. **IIFE**：形成闭包独立作用域
4. **严格模式**：意外全局变量直接报错

### 延伸：qiankun 快照沙箱

- 激活时拍下 window 快照，遍历记录新增/修改属性
- 卸载时恢复快照，把子应用污染的全局变量还原
- Proxy 沙箱（legacy 模式之后默认）：代理 fakeWindow，改动不落到真 window

:::

## 22. 小程序的双线程架构了解吗？

::: details
**问题**：微信小程序为什么采用双线程架构？

### 双线程组成

1. **逻辑层（App Service）**
   - 运行在 JSCore 引擎中，负责业务逻辑
   - 处理数据、事件、网络请求
   - 不能直接操作视图，通过通信机制传递数据

2. **渲染层（View）**
   - 运行在 WebView 中，负责页面渲染
   - 接收逻辑层的 setData 指令更新 UI
   - 每个页面独立 WebView，可并行渲染多页面

### 为什么这样设计

- **管控与安全**：阻止开发者随意操作 DOM，保证体验一致性
- **性能隔离**：JS 执行不阻塞页面渲染

### 代价

- setData 通信成本高，跨线程序列化
- 因此要减少 setData 频率与数据量

:::

## 23. React 的核心设计理念是什么？

::: details
**问题**：React 的设计理念与三大核心特性是什么？

### 设计理念

- **UI = f(state)**：声明式描述界面，状态驱动视图更新
- 保持灵活而不过度封装，由社区生态补齐能力

### 三大核心特性

1. **声明式**：开发者描述"界面应该是什么样"，React 负责 DOM 更新（对比命令式 jQuery）
2. **组件化**：UI 拆分为独立、可复用的组件，组合构建页面
3. **一次学习，随处编写**：VirtualDOM 抹平平台差异，衍生出 RN/SSR 等

### Fiber 架构意义

- 将渲染拆分为可中断的小任务单元（切片）
- 优先级调度（lane 模型，旧版 expirationTime）：高优先级更新插队
- 为 Concurrent 特性（Suspense/Transition）奠定基础

:::

## 24. AI 对话应用的流式输出，选 SSE 还是 WebSocket？

::: details
**问题**：大模型流式输出渲染，SSE 和 WebSocket 怎么选？

### 核心区别

| 对比项 | SSE | WebSocket |
|--------|-----|-----------|
| 协议 | 基于 HTTP | 独立协议（ws://） |
| 方向 | 服务端单向推送 | 双向全双工 |
| 数据格式 | 文本（event/data） | 文本 + 二进制 |
| 断线重连 | 浏览器自动重连（Last-Event-ID 续传） | 需手动实现 |
| 基础设施兼容 | 走 HTTP，代理/网关/鉴权天然兼容 | 需基础设施支持 Upgrade |

### 适用场景

- **AI 流式输出**：典型的一问一答单向推送 → SSE 更合适
- **协同编辑、IM、多人游戏**：双向实时 → WebSocket

### 选型依据

- LLM 场景只需服务端到客户端的单向流，SSE 够用且更简单
- SSE 复用现有 HTTP 鉴权与负载均衡体系，接入成本低
- 边界问题：SSE 需要 text/event-stream 响应头、禁用代理缓冲（X-Accel-Buffering: no）；连接中断时凭 last-event-id 恢复上下文

:::
